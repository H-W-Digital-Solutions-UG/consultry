# Define the Product invariant and tenant-variation envelope

## Question

Was bleibt in jeder Consultry Implementation invariant, was darf je Beratung als Default oder governed Configuration variieren, und wann ist ein Delta Template, Extension, Custom Module oder Product Candidate, damit hunderte consultancy-spezifische Implementierungen möglich sind, ohne hunderte Product Forks zu erzeugen?

## Candidate to challenge

Invariant bleiben Organization/Client Boundaries, Identity, Responsibility/Authority, Decision-versus-Recommendation, Evidence/Uncertainty, Effect Admission, Audit und Outcome Trace. Variieren dürfen innerhalb dieser Contracts Labels, Responsibility-to-Person Mapping, Stage Variants, Forms/Documents, Policies/Thresholds, Approval Routes, Workspaces/Views und Source Mappings. Wiederkehrende Custom Deltas durchlaufen einen separaten Productization-Entscheid.

Dieses Ticket entscheidet keine Schema-, EAV-, Plugin-, Graph- oder Persistenzmechanik.

Ein Candidate wird nur invariant, wenn er als rechtlich/ethisch nicht verhandelbarer Guardrail begründet ist oder sich in mindestens zwei strukturell unterschiedlichen Reference Threads bewährt. Einmalige Thread-Besonderheiten bleiben Flow-/Policy-spezifisch; die Zwei-Thread-Regel ist eine revidierbare Consultry-Heuristik, keine externe Norm.
