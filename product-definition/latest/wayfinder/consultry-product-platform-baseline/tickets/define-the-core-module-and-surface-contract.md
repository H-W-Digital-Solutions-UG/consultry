# Define the Core, module, and surface contract

## Question

Welche fachlichen Contracts muss jedes Consultry Module und jede App-/Harness-Surface vom Core erben, und welche spezialisierten Responsibilities, Objects, Detectors, Views und Source-System Effects dürfen Module besitzen, ohne konkurrierende Identity-, Attention-, Authority-, Evidence- oder Outcome-Spines aufzubauen?

## Required output

- Core-versus-Module Ownership Rules ohne finale Module Taxonomy vorwegzunehmen
- gemeinsame Case/Actor/Authority/Handoff/Evidence/Validation/Effect/Outcome-Semantik
- spezialisierte module-owned Business Work/Objects und federated source effects
- identische Case Identity über Guided App, conversational interaction, Background Operator und optionalem Harness
- Failure Case, in dem ein Modul den Core unzulässig dupliziert oder umgeht

Module- und Surface-Grenzen werden aus wiederkehrenden fachlichen Contracts und den Reference Threads abgeleitet. Eine vorhandene Architektur-, UI- oder Packaging-Struktur begründet keine Product Boundary.
