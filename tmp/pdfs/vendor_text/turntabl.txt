1. Introduction

1.1 Background and Context
Polity is procuring the provider-agnostic wallet base architecture defined in RFP-T-BACK-0006 V.2.3.1. The
work sits at the base of the R1.3.2 wallet infrastructure stack: it establishes the shared contract, persistence,
orchestration, and evidence layer that the downstream Fireblocks, DFNS, and Safeheron provider RFPs will
consume after acceptance. The RFP is explicit that this engagement does not activate a Listed Wallet Provider,
enable production signing, or move sensitive operations into live use.
Turntabl has reviewed RFP-T-BACK-0006 V.2.3.1 in full, including all 26 WBS-BASE rows, the six MR-BASE
review packages, Appendix A technical guidance, Appendix B FR/NFR traceability, and Appendix C glossary. We
submit this proposal as one fixed-price package covering WBS-BASE-01 through WBS-BASE-26, with
transparent role/rate/hour assumptions, approval-only contingency, and milestone-based payment under the
six-milestone schedule in RFP §12.2.



1.2 Proposed Approach
Turntabl proposes a pure-backend Go implementation inside the existing wallet-infrastructure-service (WIS)
module, using the direct Temporal Go SDK posture, temporal-saga-go (github.com/sunny-b/temporal-saga-go)
for SAGA compensation, gormigrate for reversible schema migrations, and the Polity Vault REST credential
gateway for all provider secret access at Activity execution time. The work is sequenced as a controlled
Strangler Fig transition: existing DFNS and Safeheron read behaviour remains reachable through compatibility
wrappers until the unified API, persistence, and evidence path are accepted. HTTP 301 redirection of legacy
endpoints is deferred to R1.3.3 per the wallet implementation baseline.
The Base RFP delivery is implementation-focused and within guardrails. We will not redesign architecture,
introduce alternative SAGA frameworks, modify Dynamic.xyz or Veriff integrations, deploy unmanaged
Temporal infrastructure, activate Nexus runtime routing, or expose sensitive operations (signing, payment, raw
broadcast, WalletConnect, transaction execution) without explicit governance approval. Fireblocks is
represented at the architecture identity, registry slot, capability descriptor, and disabled-fixture level only, in line
with RFP §4 current-state evidence.



1.3 Acceptance of Commercial and Methodological Terms
Turntabl accepts the RFP's commercial and methodological constraints:
   • AI-assisted coding is our default delivery mode and matches the RFP Effort/Budget Baseline assumption.
     We accept the 67-hour planning baseline.

3. Understanding Polity's Requirements

3.1 Core Problem
Per RFP §4 Current System Overview, the existing WIS codebase exposes provider-specific routes for DFNS
and Safeheron at internal/rest/router/router.go and internal/rest/api/api.go; internal/service/interface.go mixes
payment, broadcast, and personal-sign methods into the wallet service surface; provider credentials in
polity_vault/wallet_credentials/models.py support DFNS and Safeheron schemas only; the frontend type at
frontend/src/apps/cabinet/features/Wallet/types/base.ts permits safeheron | dfns; and internal/adapter/dfns,
internal/adapter/safeheron, and internal/adapter/fireblocks directories exist but are empty. There is no
repository-evidenced Fireblocks runtime, no repository-evidenced Temporal SDK wallet orchestration path, and
no provider-neutral persistence model.
This creates four compounding problems that the Base RFP must close before any provider-specific RFP can
begin: (1) there is no canonical operation contract or registry that all providers consume; (2) sensitive operations
are reachable through legacy paths without static or runtime negative-capability proof; (3) operation
idempotency and replay safety are not enforced by a provider-neutral ledger; (4) credential access patterns do
not yet route exclusively through the Polity Vault REST gateway.



3.2 What Must Be Delivered
The base layer comprises the following deliverable groups, each traced to its MR-BASE package below and to
its Polity baseline authority per RFP §6.1:
   • Current-state inventory and base contract freeze (MR-BASE-01): route inventory, sensitive-path register,
     persistence and credential inventory, base contract freeze note, blocked-decision log.
   • Provider-neutral contract (MR-BASE-02): ProviderAdapter interface with disabled sensitive operations,
     canonical errors and capability metadata, AdapterRegistry with conformance fixtures, feature gates and
     sensitive-operation kill switch, Vault gateway request contract.
   • Provider-neutral persistence (MR-BASE-03): reversible gormigrate steps for providers,
     provider_accounts, wallets, wallet_assets, wallet_operations, and provider_metadata; seed data and
     legacy DFNS/Safeheron read compatibility; WALLET_OPERATIONS ledger with deterministic
     idempotency; rollback package.
   • Direct Temporal orchestration (MR-BASE-04): worker bootstrap, direct client.ExecuteWorkflow
     boundary, Tier 1 ProvisionWalletWorkflow and RegisterAccountWorkflow, ten Tier 3 Canonical Activities,
     retry and SAGA compensation evidence, workflow determinism and history hygiene proof.
   • Unified API and route fate (MR-BASE-05): /api/wallets/v1/* skeleton or compatibility bridge preserving
     DFNS/Safeheron read behaviour; route fate matrix classifying every wallet route as preserve, wrap,
     deprecate, disable, or remove; sensitive-operation negative-capability closure; Dynamic/Veriff/Lukka
     non-regression; callback/webhook envelope boundary with fail-closed signature verification result
     handling.
   • Traceability and handoff (MR-BASE-06): CSV-ready traceability matrix across all 26 WBS rows mapped
     to FR/NFR/TOR gates/MR-BASE/test/rollback/owner; runbook and provider-start handoff checklist; final
     QA and release-boundary review.


3.3 Key Architectural Constraints (Acknowledged and Accepted)
We accept and will comply with the following non-negotiable constraints from RFP §5 and §7-§10:
   • The WIS Go module is the sole implementation target. We will not create parallel EKS resources, deploy
     an unmanaged Temporal Server, bypass Helm/GitOps, or store provider secrets in Helm values. Where
     infrastructure-delivery baseline handoff is incomplete, we record the blocker and use local Docker
     Compose Temporal or mock proof.

   • Credential access is executable only through the Polity Vault REST gateway at service or Activity
     execution time. WIS will not call Infisical directly, will not store raw provider secrets, and will not serialise
     credentials into workflow inputs, workflow history, logs, fixtures, frontend code, provider metadata, or
     ordinary wallet rows.
   • The AdapterRegistry rejects duplicate provider registration at startup, returns a controlled unknown-
     provider error when a provider id is not registered, and exposes capability metadata that separates
     implemented, disabled, unsupported, sandbox-only, and deferred states. Capability metadata alone is
     not authorisation.
   • Workflow code is strictly deterministic: no secrets, no SDK clients, no file I/O, no database writes, no
     direct Vault calls, no provider clients, no non-deterministic side effects in workflow state. All external
     calls and persistence writes belong inside Activities.
   • Direct Temporal client.ExecuteWorkflow is the R1.3.2 invocation path. Nexus routing remains disabled;
     wallet.nexus.routing.enabled remains false in all environments. The Nexus Service contract is registered
     on the Worker for validation purposes only.
   • Tier 1 base workflows are ProvisionWalletWorkflow and RegisterAccountWorkflow. Tier 2 Provider-
     Specific Procedures are out of base scope. Tier 3 Canonical Activities are the ten enumerated in RFP
     §20.1.9 and §11 (WBS-BASE-17).
   • SAGA compensation uses github.com/sunny-b/temporal-saga-go (the binding framework named in RFP
     §20.1.10) with forward-recovery, step-status tracking, per-Activity compensation registration, and
     reverse-order compensation on downstream failure.
   • Route migration is a controlled Strangler Fig per RFP §7. Existing DFNS and Safeheron routes remain
     reachable as compatibility wrappers in R1.3.2. HTTP 301 redirection of legacy endpoints is deferred to
     R1.3.3 and is not part of this engagement.
   • Sensitive operations (signing, payment, raw broadcast, WalletConnect, transaction execution, scan,
     provider dashboard, sensitive admin paths) are blocked by both static capability closure and runtime
     feature gates. The seven-step gate precedence in RFP §9 must pass before any provider side effect can
     occur.
   • Fireblocks is represented at the provider identity, registry slot, capability descriptor, and disabled-fixture
     level only. Fireblocks SDK lifecycle flow, webhook authentication, sandbox proof, production accounts,
     wrapper-wallet persistence, transaction/signing/broadcast/payment/WalletConnect behaviour,
     institutional vault, and Polity-held workspace-key patterns remain provider-RFP scope.

5. Security and Compliance Approach

Security is embedded throughout the engagement and is aligned to the non-negotiable security invariants in RFP
§7-§10, including the sensitive-operation acceptance rule in §10.1.



5.1 Polity Vault REST Gateway and Secret Hygiene
     • All provider credentials are requested through the Polity Vault REST gateway at Activity execution time.
       WIS does not call Infisical directly.
     • Workflows carry only non-secret identifiers and stable operation context. No credentials, raw provider
       secrets, private keys, signing payloads, payment instructions, raw transactions, or provider SDK clients
       are passed as workflow inputs or persisted in workflow history.
     • Code scans, log scans, fixture scans, frontend scans, and Temporal history scans accompany each
       affected MR-BASE package to prove no secret leakage.
     • Credential failure matrix (per RFP §9.2) is implemented as canonical errors: missing reference,
       stale/rotated, expired lease, gateway unavailable, provider auth rejected, redaction failure, audit
       correlation missing.


5.2 Sensitive-Operation Closure (per RFP §10.1)
Sensitive-operation evidence is treated as a release-blocking acceptance artefact with three proof parts:
   • Static code scan including admin-scope analysis across WIS and reachable wallet-sensitive repository
      surfaces (admin routes, scheduled jobs, frontend WalletConnect surfaces, services excluded from
      production build but reachable in dev/proof-lane), citing DSI-12-01 through DSI-12-05.
   • Runtime API inventory confirming no active route accepts signing, payment, raw broadcast, transaction
      execution, WalletConnect invocation, custody-control payloads, or unsigned raw transaction payloads in
      the acceptance lane.
   • Custodian attestation with supporting Listed Wallet Provider evidence where applicable, proving Polity
      lacks key share, signing authority, workspace key authority, and admin override authority.
Both static (compile-time capability closure) and runtime (feature gate kill switch) proofs are required. Neither
alone is sufficient.

     • Every state transition (provider registered, wallet provisioned, operation recorded, sensitive-operation

9.3 Service Credits and Delay Treatment (per RFP §12.1)
Where a milestone is delayed by a cause attributable to Turntabl (and not by Polity-provided prerequisites,
review feedback, or dependency gates), a service credit of zero point five percent (0.5%) of the fixed price
accrues per full week of delay beyond the accepted milestone date, up to a cumulative cap of five percent (5%)
of fixed price (€2,814). Service credits are applied as a deduction against the next due milestone payment as an
agreed pre-estimate of loss for delay; they are not a penalty and do not limit other Polity remedies for material
breach.
Where milestone delivery is paused by Polity-provided prerequisites, review feedback, or dependency gates
outside Turntabl's control, the corresponding milestone date and payment date shift on a day-for-day basis. No
service credit accrues during such pauses. The pause cause is recorded in the MR description or blocked-
condition register and execution resumes promptly on removal of the cause.



9.4 Warranty Holdback (per RFP §12.1)
Five percent (5%) of the fixed price (€2,814) is retained as a Warranty Release milestone, payable 90 calendar
days after Final Acceptance subject to no material defect having been raised by Polity during the warranty
window. Where a material defect is raised, the warranty window is paused until the defect is remediated to
Polity's written satisfaction, after which the remainder of the 90-day window resumes.



9.5 Change Control and Contingency Use
Any work outside WBS-BASE-01 through WBS-BASE-26, deferred work, production activation, provider-
specific runtime work, or sensitive-operation expansion requires a written change request approved before
execution per RFP §12.1. Use of the 15% contingency requires written Polity approval with documented
justification (early notification to the Programme Manager, detailed cause, impact). Overrun against Turntabl's
quoted hours is Turntabl's risk; overrun against Polity's 67-hour reference is not, by itself, grounds for a change
request.



9.6 Optional Post-Delivery Support (Separate Line Item)
As a separately priced line item (not part of the fixed-price scope), Turntabl offers post-delivery support for the
first 30 calendar days after Final Acceptance at a rate of €45 per hour, billed on a time-and-materials basis. This
covers bug fixes in base-layer code, clarifications required by downstream provider RFP teams, and minor
adjustments discovered during provider adapter development. This is optional and does not duplicate the
warranty holdback.
